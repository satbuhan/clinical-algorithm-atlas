# Clinical Algorithm Atlas

The hub page for a growing atlas of interactive, referenced
clinical-algorithm web tools — each one converted from an authored
flowchart, with the clinical reasoning and literature attached to every
step, and the algorithm itself kept byte-for-byte as drawn.

**Live site:** https://satbuhan.github.io/clinical-algorithm-atlas/

**Authors:** Dr. Özgür Karcıoğlu & Dr. Satuk Buğra Han Bozatlı

### Reserved categories

Standard, globally-recognised EM domains with no tool yet — names/order agreed
now so a future tool slots straight in without re-litigating the taxonomy:
**Obstetric & Gynecologic Emergencies**, **Renal & Genitourinary Disorders**,
**Hematology & Oncology Emergencies**, **Dermatologic Emergencies**,
**Musculoskeletal (Non-Traumatic) Emergencies**, **Environmental Injuries**,
**HEENT Emergencies**. Don't add one of these to `SPECIALTIES` in `data.js`
until it actually has a tool — an empty filter reads as broken.

Pediatric and geriatric emergencies were discussed and deliberately **not**
added as a category here — a patient population isn't an organ system, and
mixing the two axes would force every pediatric tool's card to pick one or
the other. If/when that's needed, it should be a second, independent filter
dimension (e.g. a `population` tag per tool), not a `SPECIALTIES` key.

## What this repo is

Just the hub/index page — a card gallery with search and specialty
filters that links out to each tool's own repo and live site. It holds no
clinical content itself; each tool stays in its own independent repo with
its own GitHub Pages deployment (see
[METHODOLOGY.md](https://github.com/satbuhan/aortic-dissection-protocol/blob/main/METHODOLOGY.md)
for why, and for the full build process for the next tool).

## How it's built

Plain HTML/CSS/JS, no build step, no framework.

```
index.html          page structure, masthead, toolbar, methodology strip
assets/style.css     visual design — shared palette with the individual
                      tools (same paper/ink/navy "journal" aesthetic)
assets/data.js        ← single source of truth: the TOOLS array. Add a
                      tool here when it's published; nothing else needs
                      editing for the gallery to pick it up.
assets/app.js         renders the card grid, search, and specialty filters
assets/thumbs/        a static preview image per tool (a cropped
                      screenshot of its diagram, not a live embed — keeps
                      the hub fast regardless of what a tool's own page
                      needs to load)
```

### Adding a new tool to the atlas

1. Publish the tool itself as its own repo + GitHub Pages site, following
   `METHODOLOGY.md`.
2. Take a cropped screenshot of its diagram (top ~400px, faded to the
   paper background `#F4F3EE` at the bottom edge) and save it under
   `assets/thumbs/`.
3. Add one entry to the `TOOLS` array in `assets/data.js` — `id`, `title`,
   `subtitle`, `specialty` (one of the existing `SPECIALTIES` keys if it
   fits; check the "Reserved categories" list above before inventing a new
   one — a domain with no tool yet may already have an agreed name/color
   waiting; if genuinely none fit, discuss a new category with the author
   team rather than deciding alone), `summary`, `url`, `repo`, `thumb`,
   `added`.
4. Commit and push. No other file changes needed for the gallery.
5. If the new tool's `GLOSSARY` might share a term with an existing tool's
   (same concept, not just the same string — see below), run
   `python3 tools/gen_concepts.py` and review/commit the updated
   `assets/concepts.json`. Every tool picks up the change automatically;
   no edits are needed in any tool's own repo.
6. Add the new repo name to `REPOS` in `tools/gen_search_index.py` (same
   list as `gen_concepts.py`'s, keep both in sync) and run
   `python3 tools/gen_search_index.py`, then commit the updated
   `assets/search_index.json`. This is what powers the hub's own search
   box (see "Content search index" below) — skip it and the new tool's
   content is invisible to search until the next regeneration.

### Cross-atlas concept index

`assets/concepts.json` maps a `GLOSSARY` term to every tool that
independently defines it, so that term's click-to-expand definition in
each of those tools grows an "Also covered in: <other tool> →" line that
deep-links straight to the relevant box there. Every tool fetches this
one file at runtime (best-effort, non-blocking — nothing breaks if it's
unreachable); see each tool's own `METHODOLOGY.md` ("Cross-atlas concept
links") for the runtime side.

`tools/gen_concepts.py` regenerates it by requiring every sibling repo's
`assets/content.js` (so all tool repos need to be cloned next to this one
— see the script's own docstring) and keeping only terms that appear in
2+ tools. It flags candidates; it does not decide for you. A shared
string isn't always the same clinical concept (e.g. "lipid emulsion" as a
drug vehicle in one tool vs. the LAST-rescue antidote in another), so
read each new pair's `def` text before trusting it, and add any false
positive to the script's `EXCLUDE_PAIRS`.

### Content search index

Added 2026-11-10: the search box in the toolbar (previously matching only
a tool's own `title`/`subtitle`/`summary` in `data.js`) now also searches
every tool's actual diagram content — a term buried in one node's
rationale or cautions, not just a tool's headline topic, is now findable.
Matches render below the tool grid as "Found inside N boxes," each
linking straight to `<tool url>#node-<id>` — the exact hash convention
every tool's own `app.js` already uses for the "Also covered in"
cross-links above, so **no tool repo needed any change for this.**

`assets/search_index.json` is a flat list of one entry per tool (title +
subtitle) and one entry per `NODES` item in every sibling repo (label,
sub, meaning, rationale, dose text, cautions, plus any `GLOSSARY`
full/def text that resolves to that same node — same resolution
`gen_concepts.py` uses). `GLOSSARY` terms are not indexed as their own
separate entries; folding them into whichever node displays them avoids
two near-duplicate hits for one box. Regenerated by
`tools/gen_search_index.py` (same sibling-repo-clone requirement as
`gen_concepts.py`; keep its `REPOS` list in sync with that script's).

This search is plain, case-insensitive substring matching against
English text — it does not do fuzzy/stemmed/cross-language matching. A
Turkish spelling of an English drug-class name (e.g. "betabloker" vs.
"beta-blocker") will not match; neither will a query missing a hyphen
the content actually uses ("beta blocker" vs. "beta-blocker"). This is a
known, accepted limitation for now, not a bug to chase.
